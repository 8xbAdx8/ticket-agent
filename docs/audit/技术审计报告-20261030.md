## 2. RAG 质量审计（P0）

### 2.1 121 条是怎么来的

命中文档高度集中：P02(14)、P10(10)、P09(10)、P41(9)、P04(9)、P44(8)、P01(6)。

**具体例子（`audit-examples.json`）**

| 题目 | 实际缺什么 | 返回 top1 | 分数 |

### 2.2 根因分类（按证据强度排序）

| 类别 | 证据 | 占比估计 |
|---|---|---|
| **检索算法**：单汉字分词、无 IDF、`score = 命中字数 / √文档长度`、阈值 0 | `target/rag_store.py:40-48`；41/150 条在返回文档里**完全不包含**缺失主题任何字符，仍被判命中 | 主因，覆盖全部 121 |
| **问题理解**：没有实体/槽位识别，只有 15 条属性的正则白名单 | `target/rag_benchmark.py:380-395`、`target/rag_relevance.py:27-44` | 121 全部逃逸 |
| **语料/标注**：缺失主题是“邻近主题下的细节”，题目与相关政策的共享词天然高；10 个模板 ×15 条，聚合指标被模板主导 | `test_purpose=closed_corpus_absence:<主题>`、`group_id=absent:<主题>:<n>` | 影响指标代表性 |
| **阈值**：无法用单一截断分开 | 见 2.3 | 不是可行解 |

### 2.3 阈值为什么救不了

同一批次、同一算法下 top1 分数分布：

| 集合 | min | p25 | median | p75 | max |
|---|---:|---:|---:|---:|---:|
| 可回答题 | 0.632 | 1.644 | **2.06** | 2.53 | 4.396 |
| 无答案题 | 0.0 | 0.772 | **1.26** | 1.873 | 3.571 |

两个分布大幅重叠：无答案题的 p75(1.873) 高于可回答题的 p25(1.644)。任何单一阈值都会同时砍掉可回答题；**这是排序信号不可分的问题，不是切点问题**。

### 2.4 三种过滤器的实测对比（本轮核心结论）

同一 1000 题、同一批候选（离线复算，k=5）：

| 过滤器 | 已核验 430 的 recall@1 | recall@5 | 无答案误召回 |
|---|---:|---:|---:|
| `raw`（无过滤） | 0.6233 | **0.9267** | 150/150 |
| `scope_v1`（当前基准） | 0.6233 | **0.9267** | 121/150 |
| **生产用的 `apply_quality`** | 0.1837 | **0.1988** | **29/150** |

生产过滤器把无答案误召回压到 29/150，代价是**已核验题大面积检不到**：430 题里 **228 题返回空结果**（221 题 `insufficient_evidence` + 7 题 `needs_clarification`），recall@5 只剩 **0.1988**。

> 口径说明：本次复算统一用 k=5、20 条候选池，与交付批次的 k 配置略有差异，因此 `raw` 的 recall@1 为 0.5094、交付表为 0.5188。趋势与结论不受影响；对比表内部三档使用同一口径，可直接比较。

原因在 `target/rag_relevance.py:12-26`：`TOPICS` 只手写了 13 个主题，白名单覆盖 **P01–P15 共 15 篇，语料有 57 篇，42 篇永远不可达**。

| 已核验 430 题的期望文档 | 题数 |
|---|---:|
| 完全落在白名单内 | 80 |
| 白名单为空（必被拒） | 223 |
| 部分缺失 | 127 |

无答案 150 题里：116 题白名单为空（生产会拒，巧合地“对”了），34 题白名单非空（生产会返回无关文档）。

**结论：`scope_v1` 与生产不是同一个东西——基准测的是基准自己的过滤器。** 121/150 既不能代表生产，也不能通过“换成生产过滤器”修好。

### 2.5 这段的结论

1. 无答案误召回的主因是**排序信号**（汉字重合），不是阈值、不是标注格式。
2. 现有两个过滤器一个太松（scope_v1）、一个太紧（apply_quality），共同问题是**都没有“证据是否支持结论”的判定**，只有“文档是否命中”。
3. 430 条已核验题在 `scope_v1` 下 recall@5 与 raw 完全一致（0.9267），说明**基线可保护**：任何改动不得让这 430 题的 recall@5 下降。

## 3. Agent 智能能力审计

### 3.1 追问当前就是规则匹配

`web/policy_interaction.py:199-238`：

```python
def followup_questions(question, reply, hits, asked=(), limit=3):
    topics = {key for key, pattern in families.items() if re.search(pattern, question)}   # 8 个正则族
    for key, anchors, recommendation, same_topic in FOLLOW_UPS:                          # 25 条固定文本
        supported = any(all(anchor in hit['content'] for anchor in anchors) for hit in hits)
        if supported and recommendation not in output: output.append(recommendation)
    return output if len(output) >= 2 else []
```

- 文案来自 25 条硬编码句子（`FOLLOW_UPS`，`web/policy_interaction.py:170-196`），不是生成。
- 选择依据是 8 个正则族 + 固定锚点字符串在文档里的字面出现。
- 少于 2 条就整组不显示；已问过的问题靠正则去重。
- UI 明写「不增加模型请求」（`web/conversation.py:181`），这是当前的成本设计。

**这套实现的优点必须保留**：没有证据就不出建议、不伪造检索、不额外发请求。改造不能破坏这三点。

### 3.2 局限

| 局限 | 后果 |
|---|---|
| 文案固定 25 条 | 只覆盖退票/锁座/改签/学生/儿童/报销等少数主题，P16–P57 的政策问不出追问 |
| 主题靠问题正则 | 用户换个说法（“这票还能退吗”）就落空 |
| 只吃 RAG 证据 | 车次/订单等工具结果完全没被利用 |
| 追问与回答的关联是“主题族”而非“这段证据” | 可能给出与本次证据无关但同族的问题 |

### 3.3 目标设计：模型生成 + 字面校验 + 规则回退

**输入（全部来自本轮真实记录，不允许模型自行补充）**

```json
{
  "question": "<本轮用户问题>",
  "reply": "<本轮回答，截断 800 字>",
  "evidence": [{"doc_id": "P11", "version": "...", "content": "<该 hit 原文，≤600 字>"}],
  "tool_results": [{"tool": "query_tickets", "trains": ["G7303", "G7302"]}],
  "asked": ["<历史问题>"]
}
```

**输出契约（严格 JSON，无其它文本）**

```json
[{"question": "...？", "doc_id": "P11", "quote": "<该文档原文中的连续片段，8–40 字>"}]
```

**确定性校验（模型返回后逐条过）**

1. `doc_id` 必须在本轮 `evidence` 的 doc_id 集合里；
2. `quote` 必须是该 doc 原文的**连续子串**（`quote in hit['content']`）；
3. `question` 必须以问号结尾、长度 6–40、不含“我已经/已为您/查到”等陈述性断言；
4. 与 `asked`、与已显示建议做归一化去重；
5. 通过条数 < 2 → 整体不用，走回退。

任何一条不满足就丢弃该条，**不修补、不改写、不补造 doc_id**。

**成本与授权**

- 新增 `FOLLOWUP_MODE = off | rules | model`，默认 `rules`（等于今天的成本）。
- `model` 模式必须在 Live 费用确认之外**单独勾选**「允许为追问额外发送 1 次请求」，勾选状态绑定会话，不默认开启。
- 生成时机：回答渲染后的**下一次 rerun 惰性生成**，结果按 `run_id` 缓存在 `session_state`；回答本身不被阻塞。
- 失败（超时 / 非 JSON / 校验不足 / 预算拒绝）→ 静默回退到 `followup_questions`，不弹错误、不重试。

**回退链**

```
model（已授权） → 校验通过 ≥2 条 → 显示，来源标「模型生成 · 已按原文校验」
              ↘ 不足 2 条或异常 → followup_questions()（现有 25 条表）→ 仍不足 2 条 → 不显示
```

**禁止编造的执行层保障**

- 追问只是**问题**，永不产生 `tool_call`、`rag_result`、`cited` 字段；
- 显示时必须带证据来源：`依据：P11 · <quote 前 12 字>…`，用户可点开原文对照；
- 落盘事件 `followup_generated` / `followup_fallback`，字段只含 `run_id`、`source(model|rules)`、`count`，不含任何虚构证据；
- 现有 `followup_questions` 的表驱动路径保留为**唯一的确定性回退**，并用测试锁住它「无证据就不出建议」的行为。

## 4. 修复方案

### P0-1 检索打分：单汉字 → IDF 加权 + 二元组

| 项 | 内容 |
|---|---|
| **根因** | `keyword()` 把中文拆成单字，`score = Σ(字命中)/√len`，无 IDF。高频字（车/站/时/支付）在任何文档都命中，排序由文档长度和常用字决定 |
| **代码位置** | `target/rag_store.py:40-48`（`keyword`，L41 `tokenize`、L43-45 打分）；调用方 `target/rag_service.py:57`、`target/rag_benchmark.py:472-476` |
| **修改建议** | 1) 中文按 **bigram**（`s[i:i+2]`）切分，英文/数字保持整词；2) 语料级 IDF：`idf(t)=log((N+1)/(df(t)+1))+1`；3) `score = Σ idf(t) for t∈terms∩doc / sqrt(Σ idf(t) for t∈doc)`；4) 保持函数签名与返回字段（`score`/`keyword_score`/`rank`/`doc_id`），避免改调用方；5) 保留 `threshold` 参数语义 |
| **副作用** | 全站排序变化（生产与基准同时变）；bigram 使 token 数约翻倍，内存/耗时上升但在 57 篇语料下可忽略；对英文/数字问句影响小。**不会**改变“检索命中≠答案正确”的既有边界 |
| **复现测试** | 新 `tests/test_rag_scoring.py`：(a) 构造 3 篇语料，`车` 出现在全部文档、`寄存柜` 只出现在 D3，问“寄存柜多少钱” → 断言 D3 排第一；(b) 断言同分时按 `chunk_id` 稳定排序；(c) 在 430 已核验题上跑 recall@1/@5，与基线比对 |
| **验收标准** | 430 已核验：recall@5 **≥ 0.9267**（不得下降），recall@1 ≥ 0.6233；无答案误召回不升高；单测全绿；全流程无模型调用 |

### P0-2 区分「检索曝光」与「证据支持」

| 项 | 内容 |
|---|---|
| **根因** | `no_answer_false_recall` 的定义是 `bool(ids)`（`target/rag_benchmark.py:273`）——只要返回了任何文档就算误召回。指标把“检索暴露”与“声称有依据”混为一谈，也导致“过滤器越狠分越好看”的激励扭曲 |
| **代码位置** | `target/rag_benchmark.py:259-274`、`target/rag_relevance.py:75-113`（`apply_quality` 已产出 `sufficiency.state`，但基准没用）、`target/rag_service.py:101`（只在无 hit 时发 `insufficient_evidence`） |
| **修改建议** | 新增支持度判定层，输出 `supported / partial / unsupported`：<br>① 候选必须同时覆盖**问题实体**（bigram 中 idf 最高的 2 个）与**属性槽**（数字/时间/资格词）；<br>② `rag_result` 事件增加 `sufficiency.state ∈ {insufficient_evidence, scoped_evidence, support_unverified}`；<br>③ 基准新增指标 `no_answer_false_support`（只统计 supported），**保留** `no_answer_false_recall` 作为 exposure 指标并改名 `no_answer_exposure`；<br>④ 报告里两个数并列，历史批次仍显示旧名 |
| **副作用** | 新增字段属于**新增**契约，不改旧字段值；若直接改名会影响历史报告解析，因此旧键保留并在新版增加新键；`apply_quality` 的 allowlist 语义保持不动（见 P0-3） |
| **复现测试** | 20 条人工小样本（10 支持 / 10 不支持）放 `tests/fixtures/rag_support.jsonl`，断言分类 ≥18/20；在 150 条无答案题上跑，输出 exposure 与 false_support 两个数 |
| **验收标准** | 150 条无答案题：`exposure ≤ 121/150`（不升高）、`false_support ≤ 0.20`；430 已核验题 `supported` 覆盖 ≥ 85%（否则判定过严，回到 P0-1 调打分而不是放宽白名单） |

### P2-1 分数归一与自适应截断（暂缓）

只有在 P0-1/P0-2 落地后才有意义。届时用 `support_score`（而非原始字面分）做 top1/top2 间隔判据，先在发展集标定阈值，再到验证集报告。**不要**用验收集调阈值。

### P2-2 回归门禁

把 430 已核验题的 recall@1/@5 与 `false_support` 写入 CI 门禁：任一指标相对上一版下降 >2 个百分点即失败；无答案题只做“不升高”检查。

### P2-3 语料扩充是产品决策

如果“寄存柜/支付限额/中途下车”这些主题是真实业务需求，正确做法是**补政策文档**，而不是把检索调成“看起来能答”。补语料后这 121 条应重标为可回答题，而不是删除。

## 5. 明确不建议做的事

| 不建议 | 原因 |
|---|---|
| 为了指标好看删除困难题 / holdout 题 | 直接毁掉度量；当前 sprint 已明确拒绝“case-specific blacklist”，应保持 |
| 调一个全局阈值凑指标 | 2.3 已证明分布重叠，调阈值只会同时伤害可回答题 |

| 把 `apply_quality` 直接换成 `keyword_scope`（或反之） | 一个 0.20 recall、一个 0.81 误召回，都不是可用解 |
| 在追问里让模型自由发挥 | 会产生无依据的问题；必须带 doc_id + 原文 quote 并逐条校验 |

## 6. 建议的实施顺序

1. **P0-1**（打分）+ **P0-2**（支持度）一起做，先用 430 已核验题守住 recall@5 ≥ 0.9267。
2. 再做 **P0-3**（白名单覆盖），每步都跑 150 无答案看 `false_support` 是否 ≤ 0.20。
3. **P1-3**（统一链路）把三档并排写进报告，替换掉今天“单档 + 一句风险提示”的交付格式。
4. **P1-1**（标注分区）与 **P1-2**（追问）可并行，互不依赖。
5. P2 只在 P0/P1 稳定后启动。
