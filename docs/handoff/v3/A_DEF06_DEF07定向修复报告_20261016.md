## DEF-07：执行主体与只读守卫

修复前：同一子句出现“办理”和支付/退票等动作就可能被拒；外部指引也会命中“您可以”分支。所以仅删除“办理”不足以修复两个场景。

修复后：先识别助手自身的肯定执行承诺或完成声明，再判断是否邀请用户执行操作及是否明确指向外部官方渠道；“办理”只参与执行措辞，不独立构成承诺。否定按子句处理，后续肯定承诺仍单独检查。

| 输入类型 | 离线实际行为 |

| 政策规定锁座后需在15分钟内办理支付 | ACCEPT |
| 我无法为您办理退票，您可以通过12306官方渠道办理退票 | ACCEPT |
| 我可以为您解释支付政策 / 我来说明退票规则 | ACCEPT |
| 我可以为您办理退票 / 我来帮您锁座 / 我将为您锁座 | read_only_capability_violation |
| 已为您办理退票 / 我已经帮您锁座成功 | read_only_capability_violation |
| 我无法为您执行退票 / 当前不能替您锁座 / 我不能直接为您支付 | ACCEPT |
| 我不能付款，但我可以帮你下单 | read_only_capability_violation |

## DEF-06：购买意图与锁座授权分开

原授权函数已经保留购买意图，并在“不要锁座”时撤销锁座授权。原问题是没有提前澄清，Mock 仍提议调用 lock_seat，业务守卫拒绝后只给出笼统未授权错误。

修复后，在完整工具模式、进入模型/工具之前检查购买意图与明确锁座否定的冲突。回复：

> 已了解您的购买意图。当前流程必须先锁座才能下单；本轮未锁座、未下单。您是否同意先锁座？

该轮 `steps=[]`、`tool_sequence=[]`；不调用模型、不执行工具，Mock Token 为 0。框架记录原用户消息和澄清消息，事件明确标为 `authorization_clarification`，不是模型生成结果，更不是失败模型输出的替换。

在已有路线/日期上下文中，下一轮“好，那就先锁座吧”执行 `query_tickets → lock_seat`，两工具成功；库存仅减少一次，订单数仍为 0。锁座授权不自动扩大为下单或支付授权。缺少路线时继续要求补充条件。“不要买了”停止本轮购买流程，不自动取消已有订单。

这个前置澄清仅在具备 lock_seat / create_order 的非 DeepSeek 模式启用。DeepSeek 只读模式不进入购买澄清、不邀请锁座；锁座确认的确定性决策仅新增在 LangChain Mock 模型中，没有改成真实模型决策规则。原 legacy Mock 行为和六变异机制保留。
