# 模拟改签：政策与实现准备

## 已核对的当前依据

- P02：每张票仅可改签一次；按距离原车次发车时间划分可选车次范围，改签后不退。
- P03：原车次发车后 2 小时内，可改签至当日其他有余票车次；超过 2 小时车票作废。
- P01：已改签的车票不退。
- 模拟数据仅有现成的预生成路线、车次和座位；不连接真实售票或支付系统。
- 团队 `docs/contract.md` 现有八工具和返回结构必须保留，新增工具和测试需要与 B 协调。

## 开发前待确认

- P02 的“48 小时以上”和“48 小时以内”在恰好 48 小时存在文字重叠，需要明确边界。
- 政策没有规定新旧票价差额如何结算；不能擅自声称已补款或已退款。
- P03 的“2 小时内”本次可按不超过 2 小时处理；原车次发车后至当日 24:00 的新车次须有余票。原车次跨日等时间均以本地模拟时间与实际车次为准。
- P02 的“任意车次”没有说明改签路线、车次种类或席别是否必须一致；无政策依据的限制不能擅自写成政策。

## 后端实现前需处理

- 现有订单表无改签次数、改签记录或差价状态。需采用兼容旧库的非破坏性扩展，并记录历史订单不能推断的字段。
- 旧座位释放、新座位扣减、订单变更和改签次数记录必须在同一 SQLite 事务中完成；失败不得部分写入。
- 仅当前模拟用户的有效订单可操作；具体可改签订单状态和价格差处理待确定。
- 订单是否已改签的判断应基于持久记录；后续取消/退票需遵守 P01，不能只在模型提示词中限制。
- 用户应能看到原车次、新车次、席别和费用变化并明确确认；不对接真实系统。

## 当前实现与验证

- 用户已确认：恰好 48 小时归入 48 小时以上；差价仅计算并记录模拟应补或应退，不进行支付或退款。
- 已提供出行助手表单预览与确认，并在当前会话的隔离 SQLite 中使用事务更新座位和订单，单独保存改签记录。
- 当前仅支持已支付的模拟高铁订单；政策未明确的差价结算没有执行。旧订单金额保留原支付金额，改签后的票价和差额保存在改签记录中。
- 改签后通过原取消工具按 P01 阻止退票；仅能改签一次。
- 当前没有将改签接为 Agent 的第九个 Function Calling 工具，不会写入 Agent.chat 的工具 Trace；改签记录保存在当前数据库 reschedules 表。
