# V3.9.1 架构增补（原V1.2.2保持原件）

本文件是V1.2.2及原V3.9实现的定点增补，依据本次用户授权，不重写主架构。

1. D9改为用户APPROVED方案B，详见正式决策记录；旧八工具、Baseline和旧P01不修改。
2. 退款按乘客的当前有效价格快照计算。新增不可变item/quote价格快照及当前引用；已退款明细不被改签覆盖。沿用C06：改签后的有效item仍ACTIVE，历史版本存snapshot，不伪造新的乘客或重激活REFUNDED/SUPERSEDED。
3. 提案冻结所选item、价格快照、毛额、手续费、净退款和订单quote/hold。确认时重算同一组有效明细；跨P01边界造成费用变化则旧卡失效，不能用旧确认执行新金额。
4. T031明确两个独立退款提案可竞争：仅退款豁免原pending提案唯一门禁，最多两张待确认卡；其他操作保留原唯一门禁，orders.proposal_id唯一约束不变。同一张卡仍是幂等重放，不制造第二次退款。
5. 竞争败方基于原已确认报价的冻结明细，记录独立FAILED退款请求/明细/失败交易；不改变有效状态/库存/金额。即使item已经REFUNDED，失败尝试可记录，成功迁移仍必须要求ACTIVE且成功唯一。
6. 数据库采用增量迁移002；原schema.sql/hardening.sql保持字节身份。新库在原子初始化中应用001+002；所有旧v1库（包括旧空演示库）拒绝隐式原地升级，不补造历史快照，要求独立新路径/审计副本。默认入口使用新文件simulation-v391.sqlite，旧空simulation.sqlite保留不修改。迁移故障回滚，不删库。
7. 审计发现跨时间窗净额未重验、item快照关联缺失，相关退款UI在修复与专项验证之前不启用。技术异常保持完整事务回滚、token未消费、无半套回执；业务失败提交正式失败记录与原回执。
8. T046使用直接GTFS原件证据修订版本化矩阵，原56项身份和历史失败保留；T057–T076补充规则与实际SQLite断言。

不修改CSS、公共契约、真实Provider、103内容、历史报告或原矩阵；独立审查由用户人工转交，不自动调用Harness或产生模型费用。
